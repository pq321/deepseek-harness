# Agent Note: 全局会话搜索定位至匹配消息

Status: implemented

[English](2026-08-17-global-session-search-navigation.md) | 中文

## 问题

Web 会话搜索已经可以在所有可见的实时与持久化 Session 中查找消息内容，但选择结果后只会打开 Session 的初始历史窗口。结果没有标识匹配消息，因此用户仍需扫描文本记录并手动加载更早分页。精确导航还跨越包所有权：workspace 侧边栏拥有搜索结果，而 conversation 包拥有历史分页、DOM 行、滚动和高亮状态。

## 决策

`session.search` 在 Session id 与 snippet 旁返回最强可见匹配消息的非负 `eventSeq`。宿主从已经授权的搜索命中中取得该序号，传输 schema 对其执行校验，因此客户端无需接收原始事件载荷或扩大会话可见性，即可获得稳定事件地址。

workspace 结果只为内容匹配保留 `eventSeq`。选择这类结果时会打开 Session，并发布一份临时 `ctx.conversation` 聚焦请求，其中包含单调递增的请求 id、Session id 和事件序号；仅匹配标题或 Workspace 的结果没有事件地址，仍采用普通 Session 导航。普通导航会清除待处理聚焦请求，避免陈旧搜索意图影响后续选择。

匹配 Session 的聊天视图消费该请求。如果目标节点位于已加载窗口之外，视图会在每个分页结算后再请求一页更早历史，直到节点出现或历史耗尽。节点渲染后，视图会把该行滚动到中央、遵循减少动态效果偏好、应用 2.4 秒高亮并消费请求。目标 Session 卸载时同样会消费请求；请求 id 比较可防止陈旧清理误删较新请求。

## 考虑过的替代方案

- **打开 Session 后搜索已渲染 DOM**：不予采纳，因为 DOM 中只有当前历史窗口，snippet 不必与渲染文本逐字节相同，重复文本也无法标识一条稳定行。
- **导航前加载完整文本记录**：不予采纳，因为一次搜索点击会承担无界的历史与渲染成本。现有分页加载已经提供一条有界到达目标序号的路径。
- **把分页与滚动放进 workspace 包**：不予采纳，因为该包不拥有会话投影或 DOM。临时 conversation 服务请求可保留包边界。
- **把请求事件持久化到 Session 状态或 URL**：不予采纳，因为该交互属于一次性 UI 意图，而不是持久会话状态或可分享路由约定。

## 后果

- 内容搜索结果现在会打开匹配 Session，并在消息位于初始历史窗口之外时仍显示确切消息；目标行会居中并短暂高亮。
- 搜索仍受限于相同的可见 Session 与消息 surface。新增地址只是已授权命中的元数据，并非新的读取路径。
- 很早的匹配项可能需要连续发起数次历史请求。离开 Session 会取消该意图；历史耗尽仍未找到序号时会清除请求，不会让视图陷入重试循环。
- 仅匹配元数据的结果仍在 Session 的普通位置打开，因为它们不对应消息事件。

## 验证

宿主 schema 与网关测试固定 `eventSeq` 的传递和校验。workspace 测试固定合并行为，以及只转发内容结果地址。conversation 测试固定更早分页加载、居中滚动、高亮生命周期、请求消费和陈旧请求隔离。
