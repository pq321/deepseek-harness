# Agent Note: 浏览器文件以持久引用进入输入框，但不上传字节

Status: implemented

[English](2026-08-16-browser-file-reference-composer.md) | 中文

## 问题

输入框原先会把粘贴或拖入的所有浏览器 `File` 都送进图片入口。PNG、JPEG、WebP、GIF 可以工作，其他类型一律显示图片格式警告。只在 UI 中绘制文件 chip 并不完整：提交后必须在 session 日志中留下模型可见、可回放的数据，同时不能意外读取或上传任意文件内容。

## 决策

逐 session 输入状态机现在保存有序的通用草稿附件 ID。`ConversationController` 持有浏览器对象，并在加入草稿时分类：

- PNG、JPEG、WebP、GIF 保留 object URL 预览、图片上限、base64 序列化和 Host 附件接纳流程。
- 其他 MIME 类型成为 `file` 草稿描述符；浏览器能提供相对路径时使用相对路径，否则使用文件名。该分支不创建 object URL，也绝不调用 `File.arrayBuffer()`。

`AttachmentRail` 改为 image/file 判别联合原子组件。图片仍是 64px 预览块；文件引用显示为固定高度的横向元数据条目，包含名称、MIME 类型、大小和移除操作。粘贴与整页拖放共用同一通用入口，图片数量与字节上限只计算支持的栅格图片。

提交时，文件引用经 JSON 转义后写入末尾文本段：

```text
Referenced files (content not uploaded):
- "report.pdf"
```

该文本通过既有 `session.prompt` 契约，因此会随用户消息进入日志、回放、Queue 与 Steer。线协议不增加 Host 或模型提供方无法兑现的临时文件 part。

## 浏览器路径边界

标准浏览器出于安全原因不会暴露拖入 `File` 的本地绝对路径。实现会优先使用浏览器提供的 `webkitRelativePath`（例如目录选择），再回退到 `name`；不会伪造路径，也不会暗示 Host 能够读取从未上传的内容。未来原生 shell 若需要更强的路径引用，应通过独立的可信桥接提供。

## 考虑过的替代方案

- 拒绝只做 UI chip，因为提交时它会消失，模型与回放都看不到引用。
- 拒绝新增线协议/核心 `file` 内容块，因为浏览器既没有可信绝对路径，也没有上传字节供 Host 和模型 adapter 使用；这种类型会表达系统实际并不具备的能力。
- 拒绝上传任意文件字节，因为需求明确是仅引用，而通用上传流程会引入存储、大小、恶意文件、保留期限和模型提供方格式策略，远超本次变更范围。

## 结果

任意文件类型都能保留在每个 session 的草稿中，并遵循现有 session 切换、失败恢复、提交和移除生命周期。模型只看到引用身份，不会看到文件内容。发送后的历史目前把持久引用段显示为普通用户文本；若要增加结构化历史文件卡片，需要为持久核心内容块、adapter、压缩、队列编辑和 transcript 提供完整支持。

## 验证

单元测试覆盖混合粘贴/拖放、图片上限隔离、文件条目渲染、仅文件提交、图片/文件混合序列化、不读取文件字节及附件释放。组装后的 Web 快照覆盖构建产物经完整插件图把非图片粘贴显示为文件引用条目。
